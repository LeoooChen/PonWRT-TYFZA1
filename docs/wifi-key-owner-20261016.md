# 密钥删除失败后的 DMAC/CAM 所有权

原厂依据是本机 `rtk_wifi6.ko`，SHA256
`745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
REA/Ghidra区分了通用MAC与8852C专用实现；本次依据专用函数
`mac_sta_del_key_8852c@0x250f50`、`m_security_cam_hal_8852c@0x250b94`。
Evidence ID、反编译摘录、原始结果哈希见
`artifacts/wifi-key-owner-20261016/rea-index.json`。

原厂先从DMAC表解除密钥引用，然后提交安全CAM清除，最后才把软件CAM
所有者标记清零。`tools/check_stock_key_release.py` 执行以上两个函数的
实际ARM64指令，分别让DMAC删除、CAM命令返回错误：两种错误均保留CAM
所有者；成功才释放。DMAC操作、命令提交和打包由显式回调提供，不是固件
执行或射频模拟，因此只据此确认调用顺序和软件所有权释放条件。

## 可复现缺口

原生实现只在DMAC解除引用成功后，才设置 `security_deleting`。若此前
PE撤销、TX排空或DMAC命令失败，mac80211已经请求删除的密钥没有后续清理
记录。旧函数的定向反例中，DMAC命令返回超时后 queued=0；再调用cleanup，
软件角色、硬件角色和CAM仍持有旧密钥。这是删除生命周期没有走完，不能
把删除回调的报错当作mac80211一定会重新发起删除。

## 修改

删除开始即记录目标角色和待清理CAM，并以 `security_unlink[index] =
MACID+1` 标明DMAC引用尚未确认解除。CAM分配位继续持有。已有cleanup工作
依次完成PE撤销、该密钥TX排空、当前目标角色的DMAC更新、CAM清除；只有
对应步骤返回成功才推进状态，原删除回调仍返回真实错误。

重试读取当前目标角色，保留失败后安装的其他密钥，不回放过时的整个角色。
重试DMAC命令只更新密钥选择字段，不写PN。站点释放时也先清除未完成的
DMAC引用，并撤销其pending关联，避免之后对已删除或复用的MACID再次写表。
若期间安装了新PTK，清理完成DMAC更新后重新调度已有加速准入工作，恢复
本次排空撤销的有效新密钥路径。
新增128字节关联表，沿用已有cleanup调度及CAM分配表。

## 验证与限制

`test_radio_key_cleanup.py` 编译实际三个原生函数，在ASan/UBSan下覆盖PE
撤销、TX排空、DMAC失败（硬件执行/未执行）、CAM清除失败及失败重试。
同时验证新PTK/GTK保留、MACID127编码、站点释放后MACID复用、成功删除。
模拟的CAM清除点检查所有硬件角色，仍有引用就失败。旧/新反例与定向输出
保存在同一证据目录。只构建外置ARM64无线模块；输入与当前无线源码一致，
仍有既有的缺少MODULE_DESCRIPTION提示。

这修复了可复现的删除失败残留；没有证据证明此前高速UDP测试触发了这些
命令错误，不能据此宣布双向丢包已经消失。未做实机验证、全量测试或全量
固件构建。本次只提交Wi-Fi文件，保留其他未提交改动。

另有两条研究结论，尚未修改生产代码：

- 安装失败也存在CAM分配/角色状态不一致的线索，但回滚还涉及旧密钥硬件
  PN，必须继续核对原厂的排空和PN切换，不能只补一个分配位。
- 短A-MSDU被送ARM处理；直接降低54字节快路径门槛会使以太帧补齐覆盖后续
  子帧。原厂 `amsdu_to_msdu@0xba4f4` 为拆出的MSDU另分配缓冲。本次高速
  UDP证据使用大报文，不能把这条快路径限制当作该次缺包的根因。

上述安装失败线索随后完成了普通PTK0/GTK路径的核对和修复，见
[安装失败CAM所有权](wifi-key-install-20261016.md)。该后续修复不复活已经
删除的旧PTK，重试密钥选择更新也不改写之后安装的新钥PN。
