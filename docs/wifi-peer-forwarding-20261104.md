# Wi-Fi peer forwarding handoff, 2026-11-04

The >1.5 Gbps / zero TCP retransmission target has **not** been reached. The user confirms Android stayed awake with iperf3 in the foreground throughout; do not attribute the failures to sleep. The user requested stopping further investigation and committing the reviewed fix to main.

## Confirmed BA resource defect and this change

The driver previously used the same eight records for software RX BA sessions and the eight static hardware CAM slots. Live observation found Android occupying TIDs 0,1,3,4,5,6,7 and Mac occupying TID6. Mac TID0 could no longer establish RX aggregation after reconnection. A matched capture in that state contained 89,970 matching TCP header/sequence records on Mac and AP, without missing records, duplicates or SACKs. Mac-to-AP forwarding latency was approximately 117 ms at the median; AP forwarding to the phone ACK was approximately 7 ms. Throughput was about 96 Mbps with zero retransmissions. Releasing a phone BA slot allowed Mac TID0 aggregation to establish again, but **did not fix the separate retransmission burst**.

The fix records software sessions separately from static CAM ownership. Nonzero TIDs can use hardware dynamic lookup when static slots are exhausted; TID0 can take a nonzero TID's static slot while retaining the displaced session's software reorder window. Both affected peers pass through the existing PE retirement boundary. Static removal uses the assigned CAM index; dynamic removal still retires PE and clears its software window without deleting another session's CAM. Failed firmware programming retains a deleting record for the existing cleanup retry.

The static entry ABI remains the factory C/XB range 8..15. The original module's actual `mac_bacam_avl_std_entry_idx` instructions were executed for both chips and returned `08000f00`; its `mac_bacam_init` calls the same existing users=8 initialization. Upstream Realtek also separates static CAM allocation from BA sessions and supports dynamic fallback / TID0 priority: [upstream rationale](https://git.zx2c4.com/wireguard-linux/commit/drivers/net/wireless/realtek?h=davem/net&id=3ffbb5a8b8cf6f72de12517ddf2373afc929777e). Packet numbers, sequence counters, queue limits and benchmark parameters are not reset or tuned by this change.

`tools/test_wifi_rx_ba_sessions.py` compiles the actual production RX_START, RX_STOP and removal code. It covers the observed full-table case, TID0 allocation, dynamic stop without deleting a replacement's CAM, PE retirement failure, ambiguous firmware failure and retry, all-static-TID0 exhaustion, and 225 simultaneous software sessions followed by complete cleanup. ASan/UBSan run with errors fatal. `--before` reproduces the old ninth-session rejection at cc338cb. Relevant retirement, handoff, authorization, key cleanup and offload tests also passed. PR CI runs the new test. An ARM64 module was built; a full firmware build and persistent flash of this change were **not** performed.

The RAM prototype reached ten active software BA sessions with eight static CAMs and dynamic sessions, with no pending deletion or BA error. The exact TID0 replacement and failure branches are covered by native-code tests; the full-table reconnect scenario still needs final RF qualification. The prototype's first default tests were Mac->phone 428.99 Mbps / 8 retransmissions and phone->Mac 532.27 Mbps / 2159. These are failures against the original acceptance target. Later tests with explicit `-S` QoS flags were resource diagnostics, not default throughput qualification. Final source includes a cleanup shift fix and logging/scope changes after the first loaded prototype; the final module build is separate from that loaded prototype.

## Remaining failure and strongest evidence

- Persisted firmware is cc338cb, version 0.8.5-beta. Its explicit Ethernet flow-hash normalization fixes a proven split between NI/bridge and internal mac80211 forwarding metadata. It is not a universal zero-retransmission fix.
- This turn's truly passive NDO probe reads `skb->hash` directly. The failed Mac->phone transfer had no socket-owned forwarded data, all explicit dissections succeeded, and the predicted canonical hash was identical for both paths. Removing the production helper's `skb->sk` guard is unsupported by evidence.
- `PASSIVE-FORMAL1-Mac-to-phone`: 293.90 Mbps / 2579 retransmissions. FE disabled plus a fresh Mac association still reproduced 101.48 Mbps / 1066, so PE downlink bypass is not necessary for the failure.
- `DATA-COLD1-Mac-to-phone`: 495.95 Mbps / 1217 retransmissions. All 443,533 TCP header/sequence records matched between Mac capture and AP outgoing capture; these header captures do not establish payload byte equality. Both contained exactly the same 1217 duplicate TCP transmissions; no additional reordering was observed before the AP TX queue. This localizes the residual event after that capture point, but does not prove correct over-the-air delivery. TX failure counts did not rise; CoDel dropped one MPDU and FQ collisions did not rise in this round. Most retransmissions clustered around 0.3-0.4 seconds; the first receiver SACK described a roughly 1.75 MB gap. Do not infer hardware success implies successful TCP delivery.
- `FULL-COLD1-Mac-to-phone`: 54.08 Mbps / 3359. All 56,351 fully captured IPv4/TCP packets passed checksums; retransmitted payloads were identical at the AP output. Capture changes load and this low-speed round also suffered BA capacity exhaustion; retain it as diagnostic evidence.
- TX-status monitor capture shows mainly increasing WLAN sequence numbers, with two small completion-order reversals. This is a software TX-status view, **not an external RF capture**. It does not validate CCMP PN or actual on-air payload contents.
- Latest unresolved clue: `BA-HASH-PRIORITY-default-reverse` gave 506.75 Mbps / 116. FQ collisions rose **6 -> 44923 within that default round**, despite the patched mac80211. Passive NDO data for TCP port61036 showed protocol0800 / priority0 (389206 packets) and protocol0001 / priority256 (46422), both socketless and predicting hash f237b7a5. All observed data used TID0 before classification. Thus the earlier hash fix has not eliminated every collision scenario. Trace actual hash/TID at FQ enqueue and competing tin ownership before changing hashing or priority policy. A random collision, protocol metadata changes after the helper, or another queue owner remain hypotheses, not established causes.
