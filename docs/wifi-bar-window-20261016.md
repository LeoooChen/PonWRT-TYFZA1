# BAR推进接收窗口后的PE缓存交接

## 原生缺口

BAR在ARM/mac80211中可以直接推进BA窗口头，即使没有新的数据帧被接受。
PE已有的ARM屏障会等待BAR处理结束，但原生 `rtl_ax_rx_uplink_seed` 此前
只处理至少54字节的Protected QoS DATA；24字节的BAR直接返回。屏障解除
后，旧的PE有效序号还可生效，绕过已经改变的软件重排序窗口。

例如PE缓存next SN=291、PN=1，BAR将软件头推进到294。随后SN291/PN2
仍匹配旧快缓存，旧代码会提交NI。序号4094→2的回绕也有同类结果。这些
是执行实际函数的定向反例，不是实机已捕获的缺包或攻击事件。

## 原厂调用链及结论边界

模块SHA256为
`745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
REA/Ghidra核对了 `phl_rx_handle_normal` → `phl_rx_reorder` → 上层帧列表
交付，以及 `validate_recv_ctrl_frame` → `rtw_process_bar_frame` →
`rtw_phl_rx_bar`。BAR按发端地址查站点，使用control的TID与SSN更新窗口。

`check_stock_bar_window.py` 执行原厂实际ARM64指令，验证前移、序号回绕、
不前移和旧BAR的窗口结果。单独保留旧快缓存再直接调用BAR/重排序函数，
可以得到旧SN仍被交付、头从294变295的反例；但这个入口条件不能证明
原厂完整接收路径有同一缺陷。补入正常接收入口后，以明确声明的control
metadata SN=0执行，缓存会在上层处理BAR前被撤销。

因此不能只比较BAR函数本身。前述直接调用反例不能被表述为原厂整条路径
的已证实bug；没有实机BAR描述符证据支持这种更广结论。测试输出将这两个
场景分列，站点查找、帧列表交付和bottom-half边界均由显式回调提供。

## 修复

ARM处理完BAR后，从control取得对应TID，复用现有软件快照发布逻辑。
软件BA头与已接受数据的next SN一致时继续发布；不一致时撤销该TID的
PE有效序号，设置已有pending标记，后续帧经当前软件重排序窗口。
新窗口首帧被ARM接受后，现有数据帧seed流程可重新发布PN/序号并恢复PE。

这一步在ARM屏障应答之前完成，未引入新队列、重试机制或全局停机。
PN、累计计数、guard、其他TID/站点保持；没有调整速率、160MHz或容量。

## 定向验证

`check_rx_bar_cache.py` 编译实际Linux空队列窗口释放函数和shortcut快照
函数、实际原生publish/seed函数，并与当前内嵌PE逐字节一致的链接二进制
组合执行。覆盖非零TID、窗口前移、回绕、相同/较旧BAR；仅窗口改变时
撤销旧缓存。随后明确提供一个已被上层接受的新窗口数据快照，验证下一帧
恢复NI提交。上层完整解密、BAR解析、驱动接收回调及射频没有被整体模拟。

只构建外置ARM64无线模块，输入与当前无线源码一致，PE头保持不变；仍有
既有的MODULE_DESCRIPTION提示。没有实机验证、全量测试、全量固件构建或
推送。PON及其他未提交以太网改动不包含在本次提交中。该修复不能证明此前
所有双向丢包由BAR触发，整个项目目标仍未完成。
