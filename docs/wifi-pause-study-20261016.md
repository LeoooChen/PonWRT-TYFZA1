# 原厂软件暂停与原生PE通知时序核验

本轮在Wi-Fi修复提交 `52afb80` 后继续核验生命周期，未修改PON文件。

## 原厂实际行为

`tools/check_stock_sw_pause.py` 固定使用本机原厂冻结模块，SHA256
`745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
实际执行TX/RX停止请求、PCIe回调、暂停状态判断以及暂停查询函数：

- 请求函数把软件状态置2。
- 回调完成当前一轮服务，再将状态置3；服务回调观察到的仍是状态2。
- 已停止的下一轮回调不会再次调用收发服务。
- TX在状态3后仍处理deferred ring释放；RX在状态3后仍调用恢复RX中断。
- RX暂停查询不仅检查状态3，还调用接收空闲查询；忙时返回false，空闲才
  返回true。TX查询只检查其状态。

资源判断、收发服务、延迟释放、中断恢复及空闲查询结果由显式回调提供，
状态写入与分支由原厂指令执行。它不包含真实中断时间、DMA停止时间。

## 原生PE观察及结论边界

`tools/trace_pe_pause_events.py` 对实际链接的当前PE设置两个无线上下文，
一个暂停并有待通知事件、另一个运行。原生PE在发布暂停确认后仍完成五次
通知定时器寄存器写入；另一颗无线可以继续通知，恢复后通知也能继续。

这一观察最初被怀疑为暂停/释放竞态，但仅有这些写入还不足以确认。原厂
同样有状态3之后的中断恢复动作，因此不能把“已停止”泛化为“此后不得有
任何寄存器写入”，也不能声称本工程PE定时器与原厂RX中断具有相同职责。

本轮没有修改或删除通知动作，没有把该线索算作新修复。若继续验证，必须
将原生PE通知与ARM拆除定时器的实际交错对应起来，证明其是否发生在资源
归还之后，再决定停止确认和通知的准确边界。尚未完成这种交错验证。

另检查了当前SG映射的容量处理及数据提交前的同步指令，未发现足以据此
认定新缺陷的证据。未因此变更生产数据路径。

本轮为离线原厂/原生指令核验，没有实机操作、全量测试或再次构建固件。
源码与证据哈希见 `manifests/wifi-pause-study.json`。
