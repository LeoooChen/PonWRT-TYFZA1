# 正常暂停发送时保留mac80211排队报文

## 从丢包位置倒查

原生 `rtl_ax_tx_pause` 原先先设置running=false，再等待PE请求完成、暂停
硬件调度。它没有同步停止mac80211出队。`rtl_ax_tx_queues` 只检查mac80211
队列是否停止，仍会不断取skb；提交入口因running=false返回ENETDOWN，
`rtl_ax_monitor_tx` 的错误分支会释放skb。暂停结束后，这些包已无法恢复。

定向反例运行实际pause/open、实际tasklet出队循环及实际submit准入判断，
上层队列和提交/释放回调用模型边界提供。预置32个有效待发报文，旧代码
暂停后出队32个、丢弃32个；修改后32个均留在队列，恢复后正常提交。
这定位了无线发送前的一条确定丢包路径，不需要假设空口发生什么。

## 原厂依据

本机模块SHA256：
`745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
REA/Ghidra读取 `_phl_sw_tx_pause`、`_phl_sw_tx_resume`、`halrf_tmac_tx_pause`
及 `rtw_hal_tx_pause`。原厂分别维护软件发送处理器和硬件调度暂停；不能
把scheduler寄存器停住等同于软件出队已完成暂停。

`check_stock_software_pause.py` 执行原厂软件暂停/恢复的实际ARM64指令：
先请求软件暂停、通知处理器，查询完成状态；明确提供一次未完成、再完成
的回调结果时，会经过等待边界后才返回。恢复时清除本次owner标记，再通知
处理器运行。处理器回调、owner映射及等待由模型提供，没有执行原厂skb队列。
Evidence ID、反编译摘录及原始记录哈希见 `rea-index.json`。

## 修复与生命周期

暂停开始先停止mac80211队列，并设置queues_paused，阻止期间的RPQ信用
完成把队列重新唤醒。然后synchronize_net等待已经取出的发送回调完成，
此时running仍为true；实际出队tasklet持有RCU读锁。随后才关闭提交、排空
已接受的PE请求并暂停硬件。恢复时先打开硬件/PE，再解除软件暂停；如果
原有WP信用仍不足，保持信用停止，由正常完成报告负责唤醒。

mac80211 hw指针改为在注册时绑定，而不是第一包提交后才绑定，保证首次
发包之前的暂停也能停止出队。注册失败及注销完成后解除绑定，后续NI/DMA
清理不再调用已注销对象的队列接口。未改暂停错误返回、速率、160MHz、
队列深度、信用阈值或PE程序。

## 验证边界

ASan/UBSan下的定向验证还覆盖：已取出的一个回调先完成、暂停期间到达的
信用完成不重开队列、恢复时信用不足继续等待、PE暂停失败保留排队报文并
返回原错误、hw解绑后不调用队列接口。IO、队列与网络grace period均为明确
模型边界，不是内核并发压力测试或射频测试。

另只执行既有DFS测试中的原生暂停/所有权、CAC/AP生命周期检查，没有运行
雷达分类矩阵，也没有改写其历史manifest。外置ARM64无线模块编译成功，
构建输入与当前无线源码一致；仍有既有的MODULE_DESCRIPTION提示。

此前600Mbps现场记录尚未证明缺包时间与暂停重合。因此不能把这条已复现
路径归为全部高速缺包的实机根因。PON和其他以太网未提交改动保留，本轮
没有实机操作、全量测试、全量固件构建或推送。
