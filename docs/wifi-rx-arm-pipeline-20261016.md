# RX 例外交接与双向丢包实测

本次继续使用 TYFZA1 原厂 `rtk_wifi6.ko`，SHA256 为
`745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
没有修改 PHY 速率、带宽、队列容量、PN/SN 检查或重排序超时。

## 根因和改动

`e98acab` 将物理 RXBD 补充与载荷消费分开，但处理工作环时仍等待每个
ARM 例外确认。实机有大量 RTS，以及 PHY、DFS、C2H 报告。这些例外并不
改变接收数据的 PN/SN，却同样阻塞后续合格数据。514 项载荷池仍会被占满，
随后发生实际 RXQ RDU；仅拆分补环不足以解决拥塞。

原厂 `hal_handle_rx_buffer_8852c@0x2797b4` 的实际执行确认，RX WD 类型
1、8、10 分别进入 PHY、DFS、C2H 报告处理，区别于类型0的 WLAN 数据。
原厂 `validate_recv_ctrl_frame@0xb8acc` 的实际执行进一步确认：

- BAR（0x84）调用 `rtw_process_bar_frame`。
- PS-Poll（0xa4）调用 `rtw_proccess_pspoll`。
- RTS、CTS、ACK、BA 只更新接收统计，不调用上述状态处理。

Linux 6.18.55 的 `ieee80211_rx_h_ctrl`、`ieee80211_rx_h_uapsd_and_pspoll`
和 `ieee80211_rx_h_sta_process` 也确认这些控制帧的区别。
原厂回放实际执行了分流/控制验证指令；报告解析、BAR/PS-Poll 处理体和
站点查询等被提供的回调代替，不能据此声称模拟了 RF 或处理时延。

PE 现在将 ARM 例外排入已有 FIFO。报告和普通控制帧无需阻塞后续 PE 数据。
WLAN 管理/数据、BAR、PS-Poll 仍设置状态屏障；该屏障期间后续工作按接收
顺序交给 ARM，ARM 完成整个先前批次并发布 PN/SN 后，PE 才恢复数据快路径。
没有提前归还仍被 ARM/NI 引用的载荷，也没有将缺包当作成功接收。

第一版候选把所有 WLAN 控制帧都设为屏障。实机发生持续 ARM 批次，上行
缺包明显恶化；该候选被否决。最终分类依据来自上述原厂函数的实际执行。

## 定向验证

`scripts/test_pe_rxq_backpressure.py` 执行实际链接的 MIPS PE，验证255项
ARM 积压下独立补环、有序交付256项、513次后续跨环、514个非连续DMA缓冲
的唯一所有权、NI末两项保留和序号回绕、RXQ/RPQ RDU W1C，以及数据不能
越过未完成的 WLAN/BAR/PS-Poll。RTS/CTS/ACK/BA 和报告排队时，合格数据
继续提交NI。ARM停启/DFS epoch交接及RPQ定向验证也通过；仅编译外置模块。

验证中发现 Unicorn 的全地址 MEM_WRITE 挂钩会在当前有效 MIPS 分支/跳转
组合上异常；无写挂钩及仅挂真实ISR地址均可执行同一二进制。因此将 W1C
回调限定到物理 `BAR+0x10b4..0x10b7`，保留新 RDU、W1C 及无关位不被清除
的断言。生产二进制没有为此修改指令或跳过异常。

## 实机结果及边界

5GHz 主信道44、160MHz，实际协商2SS HE。每方向目标线速300Mbps，持续6秒；
单方向对应约287Mbps UDP载荷。发送成功数只计算 sendto 已接受的包，EAGAIN
另计，不能将工具 exit2 解释为通过。没有刷写 flash，全部为 RAM 模块验证。

最后一轮 mac80211 定位在释放处记录探测包序号和原因，包含正常RX handlers
的丢弃、重排序旧序号和重复项；计数为0。该定位不覆盖进入ARM之前的帧，
也不能单独排除无线链路。该轮硬件流计数下行146280，与Wi-Fi接收146280
相等，低于发送成功146282；上行流计数146245，Mac有线接收146232，低于
发送成功146278。计数观测点属于FE输出接口MIB，不能仅凭总数给每个缺失
序号归因。Mac UDP校验错误和接收socket溢出计数没有增加。

`ctrl-drop-300-duplex`（无valid后缀）开始时Mac已自动切换到其他SSID，
AP没有关联客户端，结果全部无接收；该记录无效，不参与性能和根因结论。
另一次纯有线UDP回显对照中，27434包缺失全部对应光猫UDP RcvbufErrors
增量，不能据此宣称有线网卡、FE或空口正常/故障。

去掉诊断后的最后一次正式模块复测再次出现大量下行积压和尾丢，说明前三轮
改善不足以证明候选稳定。该轮流计数读取为0，与实际接收不符，不能用于该轮
逐段归因。**候选未采用，不能宣称修复完成，也不能将这轮大幅丢包视为正常。**
