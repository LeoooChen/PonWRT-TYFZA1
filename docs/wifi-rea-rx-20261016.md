# REA原厂接收分析与PE暂停通知交接修复

## 使用的原厂证据

REA 6.5.0 经本地Ghidra12.1.2后端分析本机原厂 `rtk_wifi6.ko`，
输入SHA256为 `745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
复用了同一输入的已存分析快照。两批查询均完成并关闭会话；8个函数的
REA Evidence ID、输入、原始记录哈希和函数字节哈希见同目录的
`artifacts/wifi-rea-rx-20261016/rea-function-index.json`。

REA反编译用于找调用和字段；关键行为再由本机原厂ARM64函数实际指令核实。
Ghidra程序地址与ELF的.text偏移分别保留，未将两种地址坐标混为一谈。

原厂 `core_rxsc_apply_shortcut` 确实调用 `process_a_control_subfield`。
`tools/check_stock_he_om.py` 执行后者及原厂HE MAC能力生成函数，确认：

- 2SS/160MHz收到有效的1SS/80MHz OM后，更新对应字段，并选择“暂停站点、
  两类硬件包释放、更新站点、恢复发送”的命令顺序。
- 相同能力不重复下发命令；超出所给本地空间流能力的输入恢复原状态。
- HTC_HE与OMI支持是分别声明的能力；给定OM支持位时，原厂生成OMI位。

站点查询、拷贝和PHL命令原语由回调提供，未实际发固件命令。本轮仅覆盖
OM为首个A-Control子字段的这些输入，不声称遍历全部控制组合。当前原生AP
没有声明OMI支持，因此本轮不擅自扩展协商能力，也不据此宣称已找到此前
实测丢包的触发帧。这条功能差异仍留待完整控制路径设计及实机证据核实。

## 从待核实线索到可复现缺陷

`7e91b33` 留下的暂停研究正确区分了两件事：原厂停止状态之后仍可能有
中断恢复等收尾动作；仅看到暂停后的寄存器写入，不足以认定故障。原厂
回调最后一轮服务完成后才写停止状态，RX暂停查询还要求处理空闲。

本轮补上此前缺少的资源释放交错。`tools/check_pe_event_release.py`：

1. 执行未经补丁的、实际链接的MIPS PE。
2. 在PE已发布暂停确认、已把通知定时器指针装入寄存器之后，暂停该执行。
3. 执行从生产 `pe-event.h` 提取、编译为宿主共享库的实际
   `pe_event_release` C函数体。它清除mailbox指针，同步IRQ，释放IRQ，
   恢复四个保存的定时器值并取消映射。保存的控制/使能寄存器为0，
   满足生产prepare函数对空闲定时器的准入要求。
4. 把该函数的内存/MMIO结果交回PE模型，继续原来那段PE指令。

旧PE仍使用寄存器中的旧指针进行五次定时器写入，把ARM恢复的
`7/0/0/0` 改成 `1/128/1/0`。这不是单看“暂停后有写入”的推断，
而是在明确释放点之后观察到了恢复状态被覆盖。

IRQ同步原语、MMIO存储及执行交错由模型提供；宿主执行的是提取的原生
C函数体，并非宣称执行了ARM机器码。没有真实IRQ时延、总线重排或设备
触发频率的测量，不能据此声称这就是以前高速缺包的唯一原因。

## 修复

PE在收到暂停命令时先完成同步，再发布暂停确认并跳过该口的通知装载。
运行中的通知路径继续使用原有逻辑。最后一轮运行先执行完、下一轮才
确认暂停，因此ARM取得确认后，才能安全收回该口所持有的定时器资源。

这里对齐原厂的完成与空闲所有权原则；原厂没有本工程同名的共享PE
定时器机制，不能声称直接照搬了原厂定时器代码。

修复后的相同验证：暂停确认后不再读取该指针，没有释放后的PE写入，
四个恢复值保持正确。双无线上下文验证确认，暂停一口不会阻止另一口
通知；积压事件无需制造新事件，恢复后即可发送。没有丢弃通知或改变
通知代数、PHY速率、160MHz、队列容量及发送完成回收合同。

## 产物与验证边界

相关RPQ验证通过，覆盖1024个MPDU、2048次BID归还、部分EQ归还、回绕及
暂停不消费报告。只编译外置无线模块；模块输入与当前无线源码匹配，
内嵌PE与受测二进制逐字节一致。MODPOST仍有既有的MODULE_DESCRIPTION
提示，没有新增编译错误。

本轮没有上机、全量测试、全量固件构建、刷写或推送。PON文件及其未提交
变更原样保留。本轮新增的确认缺陷是暂停/资源释放竞态，实机双向丢包
仍需用同负载和逐段计数复测。详细哈希见 `manifests/wifi-rea-rx.json`。
