# Wi-Fi 聚合 WP 所有权修正

## 原厂依据与确认的缺陷

本轮使用本机原厂冻结模块
`evidence/wireless-study-20261009-104746/evidence/stock/modules/rtk_wifi6.ko`，
SHA256 为 `745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
`tools/check_stock_wp_owner.py` 固定并检查该输入。没有以参考 SDK 替代原厂实现。

实际执行 `phl_recycle_payload@0x196314`、`txsc_free_txreq@0xec818` 和
`txsc_recycle_txreq_phyaddr@0xec478`：同一请求带1、5、8个 MSDU 时，原厂
逐一解除对应 DMA 映射、完成各 SKB，随后仅归还一份请求、清除一个 WP 槽，
在途 WP 计数减1，成功包计数分别增加1、5、8。核心回调被直接接到原厂
聚合释放实现；HAL/站点查找、OS/DMA释放原语及空闲链插入由显式回调提供。
这验证原厂的对象和计数关系，不模拟空口时延。

原生旧实现已经用一份 WD/WP 描述整个 A-MSDU，却为每个子包分配一个 WP
所有者槽，多余槽位没有对应的硬件发送描述符。准入上限也按子包累加，导致
聚合越大、可真正提交的 MPDU 越少。

同一份1024个 BID 的队列、每 MPDU 聚合8个 MSDU、不提供完成报告时，
执行原有生产 PE 得到：124槽已满，但实际只形成16个 MPDU，900包仍排队。
修正后同样124槽形成124个 MPDU，992包在途、32包排队；第125个 WP 仍被
阻止。队列容量、BID池、124个 WP 上限和 RPQ 配置均未扩大或调低。该反例
证明了计数粒度错误，不等价于实机吞吐提升倍数。另以1514字节以太帧、
每MPDU聚合5帧复核，旧代码仅形成25个MPDU即占满124槽；修正后形成
124个MPDU、保留620个在途子包，WP上限仍为124。

## 实现与生命周期

现在一个 WP 只对应一个 MPDU。已选子包使用 BID 头部首字串接；待发链仍
使用原有头部第4字，二者不混用。首字位于复用的 WLAN/A-MSDU 报头之前，
实际 gather-DMA 验证覆盖了报头、载荷、对齐填充及各 BID 边界。

PE 和 ARM 完成回调均只发布一个 WP 完成项。收到 RPQ 后，PE 按 EQ 信用
逐个归还其 BID；信用中断时把剩余首节点保留在该 WP，最后一个子包归还后
才释放 WP。已归还的 BID 可立即被硬件复用，后续归还不会再读它。

强制停机也遍历完整聚合链。每次成功归还后更新剩余首节点；VP复位或EQ
就绪等待失败时返回真实错误，未归还的缓冲继续保留。待发链按同样原则推进，
避免部分完成后重试重复归还。密钥、BA、站点撤销继续等待相应在途 WP。

`radio_tx` 的 `sent`/`recycled` 仍按 MSDU/BID 计数；`pending` 现在表示
占用的 WP/MPDU 数，不能再把它解释成子包数。

## RX 顺序约束

同时修正原生 RX 将每个报告都串行等待 ARM 的依赖。原厂实际分流及控制帧
验证表明，原厂将PHY/DFS/C2H报告与WLAN数据分流，RTS/CTS/ACK/BA
只作统计处理。本工程对应报告处理器也不写接收PN/SN或PS，因此这些报告
可排队交给ARM，同时后续合格数据继续进入NI。原厂报告解析回调没有在
该分流验证中执行，不能把回调模型当作整个原厂协议栈的副作用证明。

WLAN 管理/数据例外、BAR、PS-Poll 仍设状态屏障，等 ARM 确认后才处理
后续数据。与此前未采用的批量候选不同，本次不会因一个状态屏障就把后面
所有合格数据也排给 ARM。物理补环、514缓冲所有权、NI末两项保留、旧频道
DFS隔离及RDU计数保持原有合同。

## 验证及实机边界

仅执行与改动相关的验证和外置模块编译：原厂释放指令、旧/新 PE 准入反例、
实际 PE 组包与DMA边界、RPQ/EQ部分完成与回绕、RX顺序和514项唯一所有权、
ARM密钥/BA及停机回收。实际 RPQ 验证包含1024个MPDU、2048次BID归还；
部分归还后覆盖已归还BID，仍无重复读写和重复归还。

普通 ARM RX 配合 PE 下行的构建分支也按一 MPDU 一 WP 修正。其旧验证器
改为使用当前控制/context布局进入原生C入口，移除对历史bootstrap的指令
补丁；固件自动选速的fallback字段期望值另由原厂DATA描述符生成函数核实，
没有为使测试通过修改生产速率设置。

ARM64模块 `rtl_ax_ap_wp_owner.ko` 编译和符号解析通过，内嵌 PE 与受测
二进制逐字节一致。MODPOST仅有既有的缺少MODULE_DESCRIPTION提示。
没有全量测试或全量固件构建。

此前160MHz、HE2SS实测：旧独立补环版本300Mbps双向没有丢失已成功发送的
探测包，但发送端仍有EAGAIN；600Mbps双向出现大量NI尾丢和Mac发送队列
丢弃。仅解除RX报告依赖的候选在600Mbps双向仍丢包，不能宣称该处解决了
全部问题。RDU事件在无缺包的一轮同样出现，不能把事件次数当缺包数。

用户已离开设备，本轮 WP 重写未上机，不能宣称高速双向丢包已解决。后续
只需在同一160MHz与相同负载下，对齐缺失序号、WP占用、NI尾丢和Mac队列
计数；继续区分发包器未接受、Mac排队丢弃、PE/NI和无线链路。

产物、源码和证据哈希见 `manifests/wifi-wp-ownership.json`。
