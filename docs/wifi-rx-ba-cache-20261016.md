# RX BA会话切换时撤销旧快缓存

## 原厂依据

本机原厂 `rtk_wifi6.ko` SHA256为
`745328f06968003a02afa7ba7a3656f54be8f715d993f382f2a2e68acbad374e`。
REA/Ghidra分析的 `phl_rx_reorder`、`rtw_phl_start_rx_ba_session` 和
`rtw_phl_stop_rx_ba_session` 揭示了重排序对象及快缓存的所有权关系。
具体Evidence ID、坐标和原始记录哈希见 `rea-index.json`。

`tools/check_stock_rx_ba_cache.py` 随后执行原厂建立/停止函数的实际
ARM64指令：替换既有会话时，硬件BA停止/开始后分配新软件对象，撤销指向
旧对象的快缓存，再释放旧对象、发布新对象；停止时先撤销站点的会话指针
和快缓存再释放对象。回调在释放点观察到cached reorder指针为0、缓存
MACID为无效值256。HAL、分配释放与bottom-half原语由显式回调提供。

这证明原厂不会让旧窗口缓存继续指向新会话，不意味着原厂与本工程使用
同一种PE缓存布局或相同Linux协议栈。

## 原生缺口与修复

原生RX BA开始回调此前直接配置BA CAM；若该客户端已经加速，旧PE接收
状态仍可生效。多客户端共用PE时，单客户端撤销加速不会重置整个状态池，
`rtl_ax_rx_uplink_enable` 重开准入又直接沿用各TID的有效序号。
因此软件窗口已经改变时，旧缓存仍可能让收到的帧绕过当前重排序处理。

修复包含两个相连的交接点：

- RX BA开始先调用已有站点撤销流程，关闭PE准入、完成已有NI提交、同步
  最后PN/序号并等待所持缓冲归还。撤销失败就返回真实错误，不继续写BA。
- 从已撤销状态重新启用接收加速时，只撤销该站点各TID的有效序号标记及
  旧重试标记，再打开准入。PN值、累计计数、guard及其他站点均不清零。
  接下来的首帧经ARM正常接收与当前重排序窗口，再通过已有snapshot接口
  发布可用状态。已经启用的客户端重复调用enable不会覆盖PE正在用的序号。

没有重置安全PN、跳过重排序或把包直接当作完成；没有修改速率、160MHz、
缓冲池容量及队列限制。首帧重新建立缓存是会话所有权变更所必需的交接。

## 反例和验证边界

`tools/check_rx_ba_reenable.py` 将实际原生enable函数编译后，与实际链接
的PE组合执行。设置旧缓存next SN为291、声明的新窗口head为288时，旧
enable仍让SN291帧提交NI；新enable使它进入ARM例外队列。该场景的新
窗口head是输入条件，不是对mac80211重排序函数的完整模拟，不能把它
声称为实机抓到的乱序或缺包。验证还检查PN/计数/guard保持、其他站点
保持、活跃客户端重复enable保持。

实际RX_START分支的旧/新反例确认：旧分支在旧PE准入仍开时写硬件BA；
新分支先撤销，且撤销报错时没有任何硬件BA命令。原有缓冲池交接及
站点撤销定向验证也通过。

只构建ARM64外置无线模块；输入与当前无线源码一致，内嵌PE与前一轮
受测PE一致。MODPOST保留既有的缺少MODULE_DESCRIPTION提示。

另一条被排除的线索：驱动PE表只有8个TID，但mac80211建立TX/RX BA
前均拒绝TID>=IEEE80211_FIRST_TSPEC_TSID(8)，因此不增加重复边界检查。

本轮没有实机、全量测试、全量固件构建、刷写或推送。此修复针对可复现
的旧缓存复用；不能证明此前所有高速双向丢包由此触发。PON未提交改动
按用户要求原样保留，不包含在本次提交中。
