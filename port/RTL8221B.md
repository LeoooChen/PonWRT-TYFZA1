# TYFZA1 external RTL8221B initialization

2026-10-18

The 2.5G board now has a native board-specific phylib entry. The old patch
only selected HiSGMII in a generic driver. It omitted the OEM cold PHY
initialization after GPIO128 reset, and removed the OEM GPIO14 handoff
entirely. The generic 0x001cc840 callback also compares the Clause22
`phy_id`, whereas this board explicitly discovers its PHY through Clause45.
The new entry matches the board property and its Clause45 PMA model.

The authoritative source is the 2.5G unit's backed-up
`rtl8221B/rtl8221b.ko`, SHA256
`0ba23162b42e457b0628b0899e89883198aac919a14ddab91997fd9ef5710652`.
It declares GPL in its module metadata. Relevant routines are
`init_module` (GPIO14), `Rtl8221_phy_init` at 0x4de0,
`Rtl8221_wait_for_bit.constprop.0` at 0x4cc0,
`Rtl8221_enable_set`, and `Rtl8221_serdes_option_set` at 0x3df0.
The factory FDT specifies GPIO128 active-low for 30ms.

The native sequence is:

1. Standard MDIO bus reset pulses GPIO128. Its reset callback then drives
   GPIO14 high, releases its descriptor and waits 300ms before ID discovery.
   The output latch remains high; another consumer may subsequently claim it.
2. Wait for MMD31:0xa420 bits0/1. Capability discovery also waits for this
   state before reading PMA abilities.
3. Read the PMA model/revision. Revision 8 checks indirect patch version
   0x801e; version 0x20 is already initialized. Otherwise request patch access,
   wait for acknowledgement, upload the original five data tables, release
   access, program the original analog registers and commit patch version 0x20.
   Other revisions retain the original MMD30:0x75b5 preparation.
4. Disable copper through PMA control, initialize LED0 to 0x00a7, select
   HiSGMII option 1, write 0xd433/0x8020, and latch through force link down.
   phylib resume enables copper; normal phylib Clause45 operations own
   advertisement, link reporting and subsequent suspend/resume.

The patch constants are data copied from the exact original module; register
order and duplicate writes are preserved. The initialization is rewritten in
native C. There are no SDK wrappers, silent skips, retry fallbacks, or fixed
PHY IDs injected into the device tree. MDIO errors stop initialization.
The mode setter follows the OEM's nonfatal force-down acknowledgement timeout:
it releases the request, reports a warning and lets phylib resume the PHY.
Actual MDIO read/write errors and failure to release the request remain fatal
for that port.

Only the 2.5G device tree declares GPIO14, GPIO128, the external PHY and
its S3 consumer. Four-GbE variants neither toggle these pins nor match the
new PHY entry. NI still owns the shared LED controller registration; PHY
initialization now owns its function register so it is restored on
reinitialization.

Validation is deliberately limited to these changes:

- `scripts/test_rtl8221b_oem.py` executes the actual ARM64 OEM functions and
  the native C against the same register state. Revision 8 without its patch
  matches 1093 read/write events, including 1075 writes. Already-patched
  revision 8 and revisions 9/10 match 19 events each. Nonzero unrelated register
  bits are included in the comparison.
- The same check verifies the GPIO14 ownership and 300ms delay against the
  original module initializer, actual poll conditions, selected bus failures,
  and PHY model/board matching.
- Both production DTs pass the existing board-variant check, including
  absence of external-PHY properties on the four-GbE board.
- Realtek PHY, MDIO and NI objects compile for ARM64 with the project's
  kernel configuration. The existing PHY LED control check passes.

Receipts for the initial offline work are under
`artifacts/rtl8221b-cold-init-20261018/`.

## 2026-10-19: 2.5G hardware failure and port isolation

On the 2.5G board running the 0.8.0 beta-era initialization, the force-down
poll at MMD31:0xa434 timed out. The live register was 0x5600 with bit2 clear;
the SerDes option register was already 1. Treating this acknowledgement as
mandatory differed from the OEM. Executing the original ARM64 setter with
0x5600 and 0x1e00 confirms that it polls 100 times, releases a400 bit14 and
returns success in both cases. The previous test only executed the OEM with
an immediate ACK, so its asserted timeout behavior missed this incompatibility.

The native setter now warns on this particular timeout and returns the release
result. Ready/patch timeouts, bus errors and release errors still propagate.
On the connected 2.5G unit, executing the corrected production initialization
against the isolated external PHY returned 0; resume returned 0, PMA control
was 0x2058, a420 was 0x0023, SerDes mode was 1 and a400 was 0x1040 (force-down
released). This confirms initialization, not copper negotiation or throughput.

The NI driver previously unwound every extra LAN and LAN1 after any port
failed. All five LAN registrations now have independent resource cleanup,
including LAN1: a failed PHY, allocation, FE admission or registration only
removes that port. A failed LAN5 LED registration leaves its data path up.
Diagnostic attributes and the Wi-Fi notifier also report their own failures
without removing wired ports. Shared MMIO/DMA/QM allocation remains a genuine
prerequisite before any port is published; normal driver removal still tears
down the device's resources.

`scripts/test_lan_probe_isolation.py` executes the production registration and
cleanup functions with 90 fault cases across both board variants, plus optional
service failures. The OEM comparison now executes the missing-ACK OEM branch
and checks that MDIO release failures remain fatal. The production DT/FIT
selection check still covers four-GbE and five-port boards without changing
either device tree. PHY and NI ARM64 objects compile with the project config.
LAN1 has also been verified at 1000/full on this unit. Full-image 2.5G
negotiation and throughput remain separate hardware checks.
